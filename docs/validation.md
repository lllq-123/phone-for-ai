# 验证记录

这里区分日用版本的生活场景实测与新整理公共版的构建、协议及设备测试。相同的原理不能替代新包自己的验收。

## 公共版 v0.1.2：2026-10-06

起因：有使用者在一加 8T / Android 14 / Magisk 26.1 上照教程搭完，实时投屏先显示“等第一帧画面…”，约 10 秒后报“手机没能启动投屏”。她用 `setenforce 0` 对照确认是 SELinux 挡住了手机伙伴去连接 Root 进程开的插座，自己补规则后恢复。0.1.2 改由 Root 启动的 scrcpy 主动连接手机伙伴，并把报错拆成 Root 授权被拒、组件没能启动、连接超时和中途出错。

本轮在一加 8T / Android 14 / Magisk 30.7 上，用独立 APK、独立测试服务和临时 HTTPS 入口验证。测完卸载测试包，撤销临时 Root 授权与路由，服务器入口逐字恢复。

| 检查 | 结果 |
| --- | --- |
| 反向连接与画面 | scrcpy 以 Root 启动后主动连入；“手机连上了”之后约 0.7 秒收到首帧，576×1280 H.264。收到的码流用 ffmpeg 解出首帧和末帧，都是正确的手机画面 |
| 网页“桌面”键 | 发送后末帧为系统桌面 |
| 正常停止 | 停止后 5 秒内手机上没有残留的 scrcpy 进程，本次会话的进程回执已删除 |
| Root 授权被拒 | 把测试包的授权改为拒绝：连上后约 0.1 秒显示“手机伙伴没拿到 Root”；Magisk 只记录一次拒绝（su 退出码 13），没有为清理再弹授权框 |
| Android | `testDebugUnitTest assembleDebug` 通过，20 tests；versionCode 3 |
| 服务端与网页 | `pytest -q`：18 passed；`node --test`：5 passed |

本轮查实、已在代码里处理的两点：

- **scrcpy 4.1 启动后会把自己从 root 降为 shell 用户（uid 2000）**，所以手机伙伴核对连接身份时接受 0 和 2000。普通 App 不可能以这两个身份连接。
- **这台 Magisk 下，su 会在 scrcpy 仍在运行时先返回 0。**手机伙伴不把 su 退出当作 scrcpy 退出：只有 su 明确拒绝授权时才提前报错，其余情况等满 10 秒，结束时按进程回执清理。

验证边界：我们手上的 Magisk 30.7 本来就放行旧版那种连接，**没有在会挡住旧版的 Root 方案（Magisk 23.0–26.1、较早的 KernelSU 系、APatch）上实测 0.1.2**；这些方案对 Root 进程主动连接普通 App 放行，依据是各项目的源码。没开无障碍和后台权限的测试包，按“桌面”后被 ColorOS 冻结、画面断开；开启权限后的后台表现以 0.1.1 的验证为准。

最终交付 APK SHA-256：`33995fbb06c16c04bc9c37d8789e72fdcabcc2f8bd5160c83292439d09156cbb`。

长传先完成于本轮后台修复阶段；随后补媒体索引、重复唤醒生命周期与漏广播校正，再在最终 APK 上完成上表的连续唤醒、锁状态、后续操作及小图片助手检查。没有把早期构建的所有检查都写成最终文件重新跑过一遍。

本轮查实的原因与处理：

- **Android 白名单不能代替 ColorOS 后台权限。**只设 deviceidle/AppOps 时，系统日志仍反复冻结新 App，第一轮在 1,425,408 字节后留下未知 delivered 回执；助手停止后只查原 ID，明确放弃，没有追加重试。开启“允许完全后台行为”并重新启用本次无障碍后，完整长传通过。
- **非安全滑动锁也必须等它真正退出。**唤醒改为等待亮屏、锁屏消失及画面稳定；每次创建新的短命 WakeActivity，避免系统权限弹窗留下旧实例，导致第二次不亮屏。熄屏广播漏送时由已有心跳校正持锁状态。
- **扫描广播返回成功不能证明相册收录。**这台系统的旧广播没有收件者；图片助手改用 MediaProvider 扫描，并查询对应路径和文件大小后才报告成功。

首次使用按[安装说明](setup.md)开启电池优化豁免、ColorOS 完全后台行为，并处理“在锁屏上显示”等系统提示。持续待命耗电增量、全天稳定性、其他厂商及开机自启动不在本轮验收范围；安全 PIN/图案/密码仍由本人解开。本轮没有发帖、发聊天消息或下单。
